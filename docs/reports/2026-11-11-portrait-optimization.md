# 立ち絵の縮小と WebP の埋め込み: 大きさと処理時間の計測

## はじめに

課題 obs-voice-spotlight-5dt.12 の計測の結果です。立ち絵は、適用のときに元の画像を表示の高さの 2 倍まで縮小し、WebP で書き出して data URI で埋め込みます。埋め込む画像には、1 枚 1,048,576 バイト、合計 4,194,304 バイトの上限があります。超えるときは、倍率を 2 から 1.5、1 と下げ、続けて WebP の画質を下げます。この計測は、WebP の画質の既定値を決めるために行いました。

## 検証環境

- Windows 11、`cmake --build --preset windows-ci-x64` で作った RelWithDebInfo の実行ファイル
- Qt は `.deps/obs-deps-qt6-2026-10-23-x64` のもの。`QT_PLUGIN_PATH` に同じ Qt の `plugins` を、`PATH` に `bin` を渡して実行した
- 画像は依頼者が貸した立ち絵 7 枚。本文ではサンプル 1〜7 と呼ぶ。サンプル 1〜3 はネットワーク上の共有フォルダー、サンプル 4〜7 はローカルのディスクから読んだ

## 検証方法

計測用の実行ファイル `speaker-spotlight-image-bench` を使いました。ソースは `tests/image-bench.cpp` です。プラグインと同じ `src/portrait-image.cpp` の関数で、元の画像を読み、縮小し、書き出します。`ENABLE_TESTS` のときだけビルドし、ctest には登録していません。

各サンプルについて、元の画像の読み込みを 1 回計りました。続けて、表示の高さ 150px と 600px のそれぞれで、倍率 2・1.5・1 に縮小しました。縮小した画像を、WebP の画質 100・90・80・75 と PNG で書き出しました。縮小と書き出しは 3 回ずつ計り、中央値を採りました。画質 100 と PNG では、書き出した画像を読み戻し、縮小後の画像と画素を比べました。不透明度が 0 の画素は、色を比べず不透明度だけを比べました。

最後に、プラグインの段の列で書き出した大きさを使い、プラグインと同じ `plan_embedding()` で選ばれる段を求めました。

実行のコマンドは次のとおりです。

```powershell
$qt = "D:\work\obs-voice-spotlight\.deps\obs-deps-qt6-2026-10-23-x64"
$env:PATH = "$qt\bin;$env:PATH"
$env:QT_PLUGIN_PATH = "$qt\plugins"
& build_x64\RelWithDebInfo\speaker-spotlight-image-bench.exe .tmp\2026111118-sample-portraits.txt .tmp\2026111119-bench-output
```

生の出力は `.logs/2026111116-image-bench.log` です。同じ計測を 2 回行い、1 回目は `.logs/2026111114-image-bench.log` です。

### 可逆と透過

画質 100 の WebP と PNG は、全条件で、読み戻した画素が縮小後の画素と一致しました。全条件で、縮小後の画像に透過があれば、書き出した画像にも透過がありました。

### 段の選び方

プラグインの段の列は、倍率 2・1.5・1 の画質 90、続けて倍率 1 の画質 75・60・50 です。表示の高さ 150px と 600px のどちらでも、7 枚は 1 枚ずつでも全員の組でも最初の段 (倍率 2、画質 90) が選ばれました。

### 2 回の実行の比較

1 回目と 2 回目で、書き出した大きさは全条件で一致しました。時間は、サンプル 1 の読み込みが 2 回とも 462 ms でした。

## 考察

### 既定の画質

既定の画質は 90 を提案します。

表示の高さ 150px では、画質 90 の 1 枚の最大は 22,368 バイトで、上限の 2.1% です。600px でも最大 173,146 バイトで、段を下げずに収まります。上限に対する余裕は大きく、画質 80 や 75 に下げて得られる大きさの差は、上限との関係では意味を持たないと考えています。

画質 100 の可逆でも、7 枚は 600px で段を下げずに収まります。ただし書き出しの時間は、600px・倍率 2 で画質 90 の約 3〜5 倍です。7 枚の合計では、画質 90 の約 2.0 秒に対して約 4.2 秒です。適用の処理の間は OBS の画面の操作が止まると推測します。2 倍に縮小した画像をブラウザーがさらに縮小して表示するため、画質 90 の劣化は配信の画面では見分けにくいと考えています。見た目の判断は依頼者の目視に委ねます。

### 段の引き下げ

依頼者の 7 枚では、段の引き下げは働きませんでした。引き下げは、写真のように圧縮しにくい画像や、上限に近い大きさの画像のための備えです。引き下げの動きは、偽のエンコーダーを使う単体テスト `tests/core-tests.cpp` で確かめています。

### WebP を書き出せない環境

PNG でも、600px・倍率 2 の 7 枚は 1 枚の最大 909,372 バイト、合計 3,745,715 バイトで上限に収まりました。ただし、どちらも上限に近い値です。立ち絵が 8 枚以上の場合や、大きな画像では、PNG の環境で倍率の引き下げが働くと推測します。

### 処理時間

7 枚の時間の合計のうち、約 1.2 秒は元の画像の読み込みです。読み込みは画質によらず発生します。同じ条件の再適用ではキャッシュを使うため、画素の読み込みと書き出しは発生しないと考えています。OBS の中での時間は計っていません。サンプル 1 の読み込みの 462 ms には、ネットワーク上の共有フォルダーからの読み込みと、Qt の画像のプラグインの初回の読み込みが含まれると推測します。内訳は計っていません。
